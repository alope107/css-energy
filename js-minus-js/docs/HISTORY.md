# History: how the design got here, and what didn't work

This was reconstructed from three sources:

- **File timestamps, docstrings, version diffs and result logs.** These are mostly preserved under `archive/`.
- **Earlier claude.ai chats.** Links are given where they matter. Those chats ran in other sandboxes, so their
  files aren't in this repo unless noted.
- **Notes from this conversation.**

Every number here has its source in [BENCHMARKS.md](BENCHMARKS.md).

**Notation.**

- "Self-compile" is the original workload: the self-hosted `jsc.js` compiler, running as ROM, compiles a
  FizzBuzz source at run time and then runs it.
- "Direct fizz" is the same FizzBuzz compiled ahead of time straight into ROM.

## In this codebase

### Phase 0: HarfBuzz spikes (2026-10-09 morning; `archive/spikes/hb`, `archive/spikes/first_deliverable`)

- **Probes**: lookup budgets, a LUT font built from kern pairs, a variable-font LUT, and font LUT vs CSS `if()`
  mux. Most of their numbers weren't saved.
- **The key trick**: one GSUB Lookup referenced K times in the LookupList, so one shaping runs K VM steps.
  - The first toy VM font (`vmfont.py`) ran up to 16,000 aliased steps per shaping.
  - 32,000 was rejected by the sanitizer's limit of 16,384 subtables.

### Phase 1: the pure-CSS stack VM (`archive/machine/gen_vm.py`)

- **ROM**: one `if()` branch per word.
- **RAM**: elements whose remembered width is the word. Reads use `anchor-size()` ports.
- **Clock**: K instructions per frame, one per layout pass, because remembered sizes update only once per frame.
- **Result**: self-compile 3,609 s, direct fizz 316 s. It is the baseline everything below beats.

### Phase 2: the font CPU (`cpu.py` → `cpu2.py`)

**The idea.** The CPU state becomes a line of glyphs, and S micro-cycles of a cached CPU run as GSUB lookups
during one shaping. CSS services the traps.

- **Model**: `uarch.py`, value-level.
- **Font**: generated by `cpugen.py` through the hand-written GSUB assembler `otl.py`.

**Two cache designs.**

- **v1 (`cpu.py`)**: a FIFO cache plus an evict buffer, with data moving between lines.
- **v2 (`cpu2.py`)**: a ring with a victim pointer, so data never moves between lines. The core is laid out
  digit-major so contexts stay a few glyphs long. HarfBuzz's cost is roughly rules tried times walk distance,
  measured with `walkbench.py` and `stagetime*.py`.

**Measurements.**

- First browser numbers: 17.5 steps/s, 3 fps.
- Self-compile in 1,287 s, already 2.8× faster than the CSS VM.
- A related chat ([CSS harfbuzz performance optimization](https://claude.ai/chat/a0443640-884f-4ac4-a31a-6996723b78a2))
  established that traps, not the micro-cycle budget, limit the instructions per shaping. It also found that
  CSS style and layout per pass dominated, not shaping.

### Phase 3: correctness at any zoom (`zoomfix.py`)

- HarfBuzz positions are 16.16 fixed point and Chrome snaps glyphs to device pixels, so one font unit must be
  exactly one device pixel.
- The page finds the device-pixel ratio with resolution media queries.
- `diag.py` shows the width Chrome measures next to the width HarfBuzz computes, per span.

### Phase 4: decode-tree RAM (`memtree.py`)

- **Before**: one `@container` rule per cell per write channel.
- **After**: a decode tree whose off-path nodes compute constants, so restyling stops one level down.
- **Same change**:
  - the wall clock moved to `#clk` so it no longer restyles memory;
  - the issue counter saturates so frames can settle.
- **Effect**:

  | Measure | Before | After |
  |---|---|---|
  | Style + layout per pass | 70 ms | about 20 ms |
  | Direct fizz | 87.5 s | 22 s |
  | Self-compile | 1,287 s | 385 s |

### Phase 5: 4-word cache lines (`uarch4.py`, `cpu4.py`, `gen_fvm4.py`)

- **How it was chosen**: model sweeps of trap distance (`sim2.py`, `sim3.py`) picked B = 4.
- **RAM**: four banks, so a whole line fills or writes back in one service.
- **Effect**: self-compile 385 s → 250 s.
- **Sweep**: N16 S32 was best (248 s); the spread across configurations was about 7%.
- **S = 48**: one run with S = 48 never executed a step, and the cause wasn't found.

### Phase 6: the compiler moves out of the ROM, into CSS (`compiler/`)

**Why.** With jsc in ROM, compiling FizzBuzz took about 365 s on the CPU and running it about 14 s
([JS in CSS compiler architecture](https://claude.ai/chat/d3f41ebe-8d70-4fc1-b81c-85cdc71b9e66)). That chat
proposed a data-parallel pipeline instead of a faster CPU.

**What was built.**

- **Reference**: `cc_ref.py`, a one-step-per-character transducer written the way CSS can compute it. It
  produces code identical to jsc's for the same program (`cmp_jsc.py`).
- **CSS form**: the DSL `dsl.py` / `cc_dsl.py` writes that step once. It evaluates in Python and compiles to CSS.
- **Chain**: one nested element per character. The ROM shrank to the runtime library.

**Successive generators.** Times are Chrome style-recalc, FizzBuzz:

| Generator | What changed | Recalc |
|---|---|---|
| `ccpage.py` | whole compiler step on every character | 8,562 ms |
| `ccpage2.py` | lexer on every level; parser only on levels that end a token | 3,104 ms |
| `ccpage3.py` | parser variants per (mode, token) chosen by container query; tables become delayed writes; labels become anchors | 914–1,573 ms |
| `ccpage4.py` | lexer specialised per character, parser rules bucketed by the previous character's class | 318 ms |

**Bugs found along the way.**

- `@container style()` doesn't match integers of 256 or more.
- Registered integers lose precision crossing `var()`, so 20-bit words became signed.

### Phase 7: typed input (`readback/ui_rb.py`, `compiler/ccpage5.py`, `gen_fvm4.py UI=1`)

The editor readback was joined to a compiler that reads the latches through view-timeline registers. Four
problems had to be solved:

1. **Container queries over 256.** The variant id was split into small fields.
2. **Cost scaling with registered properties.** At about 13,000 registered temps, animations became very slow.
   Pooling the temp names cut it to about 2,600; the final page has about 3,800 `@property` rules in total.
3. **Animating every chain level.** Each level cost about 3 ms. Sources moved to one element per line and one
   per 32 tokens.
4. **The 512-deep nesting limit.** The pages became XHTML with `display: contents` levels.

The scan was also reworked:

- It is frame-locked, because a time-driven scan skipped columns at low frame rates.
- Its range is fixed at 64 columns, because a range taken from the editor's width flickered.
- Freezing the compiler's animations failed (see the dead-end list), so the chain is shown and hidden instead.

**Result**: the first typed-input page. Run → compiled in about 5 s; FizzBuzz halted about 27 s after Run.

### Phase 8: correctness and tests (this conversation)

**The trigger.** The user reported that `var a = "hi"; console.log(a)` printed 4352. The problem was that a
string was its bare address.

**Tests.** Five test levels were built (see [ARCHITECTURE.md §5](ARCHITECTURE.md#5-tests)). The first
reference run passed 37 of 53 programs.

**Fixes.**

- **Values**: tagged strings, and static types (boolean, string, number, unknown) with matching print routines.
- **Operators and assignment**: short-circuit `&&` / `||` with value semantics; `let` / `const`, `===`, compound
  assignment.
- **Syntax**: `/* */` comments, single quotes, escapes, multi-argument `console.log` with joining, `++x`.
- **Statements**: braceless bodies, `break` / `continue`, semicolon insertion.
- **New errors**: undefined functions, and overflow of the globals and string areas.
- **`else if` chains**: these now share one wrapper.

**Keeping the code fast.**

- **Unreachable blocks**: with a known starting mode, `Prog` folds them away (`FALL`). This halved the
  generated CSS (91k → 47k temps).
- **Do-nothing variants**: they share one pass-through rule.
- **The runtime library was tuned against the machine model** (`tools/traps.py`):
  - The string tag moved from 2^19 to 2^18. Untagging with +2^19 overflowed the 20-bit range.
  - The tag constant lives in a RAM cell instead of being built with SHL13, which traps.
  - That cell is 4096, on a line that is always in the cache. At first it shared a line with the string data,
    which added 23 misses to FizzBuzz.
  - The newline moved back into the callee (`…Ln` entry points), because two extra code words per
    `console.log` pushed FizzBuzz's code out of the 16-line cache.
  - Runtime type checks sit where they are free (in `printNum`'s negative branch).
- **Net effect** on FizzBuzz: 193 shapings, against 187 before the language changes (+3%).
- **Compile speed**: about 820 ms in the L3 harness, against about 1,050 ms at the start of the session.

## Dead ends and superseded approaches

| # | Tried | What happened | Replaced by |
|---|---|---|---|
| 1 | Pure-CSS VM as the CPU (`gen_vm.py`) | 3–4× slower than the font CPU at every stage (3,609 s vs 1,287 s; 1,502 s vs 385 s) | font CPU |
| 2 | One `@container` rule per RAM cell per write channel (flat RAM) | style + layout 70 ms per pass | decode tree, ~20 ms |
| 3 | FIFO cache with an evict buffer, data moving between lines (`cpu.py`) | long contexts, expensive in HarfBuzz | ring with a victim pointer (`cpu2.py`) |
| 4 | One-word cache lines | more traps per instruction | 4-word lines (385 s → 250 s) |
| 5 | fontTools' feature compiler for the CPU | can't alias one lookup many times | hand-written `otl.py` |
| 6 | More than 16,384 aliased subtables | rejected by the sanitizer | at most 16,000 per font |
| 7 | S = 48 micro-cycles per shaping | the run never started; not investigated | S = 32 |
| 8 | Unsigned 20-bit words in registered properties | precision lost through `var()` (1048575 → 1048580) | signed words |
| 9 | Self-hosted jsc compiling at run time on the CPU | compiling took ~365 s vs ~14 s running | compiler in CSS |
| 10 | Whole compiler step on every character (`ccpage.py`) | 8.5 s recalc | lexer/parser split, then variants |
| 11 | One generic parser on every token level | 3.1 s recalc | container-query variants |
| 12 | Specialising on every punctuation value at once (46 MB of CSS) | slower than coarser keys (1,813 vs 914 ms) | `mt`, then class-bucketed lexers |
| 13 | Variant ids of 256 or more in style queries | never match | ids split into small fields |
| 14 | Symbol and function tables carried as parser state | every level copies them | delayed table writes through ports |
| 15 | Animating each character level from its own latch register | ~3 ms per level | one source per line |
| 16 | 13k registered temp properties | animations very slow | pooled names (~2.6k) |
| 17 | HTML documents | parser stops nesting at 512 | XHTML |
| 18 | Pausing or freezing the chain's animations once the text was read (`archive/readback/tl1–9`) | play-state comes from the base style; animations created paused don't take the timeline's value | keep sources running; hide or show the chain with `display: if()` |
| 19 | A time-driven editor scan | skipped columns at low frame rates | frame-locked scan |
| 20 | Scan range taken from the editor's width | flickers, because the sentinel's width is the code being read | fixed 64 columns |
| 21 | Inherited per-frame driver state | restyles every cell | non-inherited state |
| 22 | Two end-of-input levels | redundant once the parser chain was separate | one NUL slot |
| 23 | Line sources paused after the read | unreliable capture | sources keep running |
| 24 | Strings as bare pointers | printed as numbers (the 4352 bug) | tagged pointers |
| 25 | Tag offset 2^19 | the untag overflowed the 20-bit machine | 2^18 |
| 26 | Building the untag constant (`262144` needs SHL13) | an EXT trap on every string print | constant in a RAM cell |
| 27 | The constant in the string area's first cell | +23 cache misses on FizzBuzz | cell 4096, on a hot line |
| 28 | Separator passed as an argument, or emitted by the caller | +9% steps, or code overflowing the cache | `…Ln` entry points |
| 29 | A fresh wrapper per `else if` | a chain of 8 branches overflowed the control stack | the inner `if` reuses the outer `else`'s wrapper and label |
| 30 | One set of label ports per possible deflab site | 26–35 ports per level | collected `&&`/`||` labels and pruned unreachable blocks (22 ports) |

## Proposed and never tried (open leads)

These come from earlier chats unless noted, and none has been measured on the current machine.

### Fewer traps

The machine runs about 50 steps/s on the page, and traps end shapings early, so these matter most.

- **Do SHL13 in the font.** It's a linear shift.
- **Do multiply-by-small-constant in the font.**
- **Treat dirty lines above SP as clean.** They never need a write-back.
- **Bring back an eviction buffer.** It removed most WFAILs in v1.
- **Prefetch the next sequential line.**
- **Service read misses inside one layout pass.** A toy chained 8 shapings in one layout; only writes are stuck
  at once per frame.
- **Pack two characters per word.**
- **Buffer PUTC** in the glyph string and flush it at the next trap that happens anyway.
- **Keep the top of stack in registers.**

### More shapings per frame

- **Chain dependent shapings in one lifecycle update**, using container-query layout→style→layout loops
  ([JS-in-CSS multicore](https://claude.ai/chat/91b25db5-fef0-4893-9055-42e5003ad7e5)).
- **Try N = 16, S = 64.** That configuration was never run.

### Specialisation

- **Per-program CPU fonts.** Compile hot blocks to GSUB (a Futamura projection), or use superinstructions taken
  from traces.

### Compile time

At 2–7 s on the page, about half of compile time is the readback sweep.

- **Read several columns per frame.**
- **Lex in parallel**, with a prefix scan over the DFA's transition functions.

### Other compute surfaces

These were measured in [CSS JavaScript interpreters speedup](https://claude.ai/chat/427a6452-26e2-4ff6-8289-3177eab3cabc).

- **`@function` / nested-grid lookup chains**: 300–600 dependent lookups resolve in one update.
- **avar2** can compute arbitrary two-input lookup tables (Chrome 148 and later).

### Language

- **Widen the console.** It is 8 columns, and output RAM costs per cell.
- **Strings**: building and comparing them needs a heap.
- **Booleans as parameters.**
- **Specific error codes on the page**, instead of 99.
